# API Contract – `/chat`

This document defines the **canonical JSON contract** for the `POST /chat` endpoint used by the Flutter app and implemented by the FastAPI backend.

The backend will validate incoming payloads using Pydantic models that mirror these structures.

---

## Endpoint

- **Method:** `POST`
- **Path:** `/chat`
- **Content-Type:** `application/json`
- **Auth:** None (local, trusted environment for V1)
- **CORS:** Enabled for local development; see `backend/.env.example`.

---

## Request

### JSON Shape

```json
{
  "session_id": "string",
  "messages": [
    {
      "role": "user",
      "content": "Hello, Jarvis",
      "ts": "2024-01-26T12:34:56Z"
    }
  ],
  "client": {
    "platform": "android",
    "app_version": "0.1.0"
  },
  "settings": {
    "response_style": "normal"
  }
}
```

### Fields

- `session_id` (string)
  - Identifier for the current conversation session.
  - For V1, the mobile app may use a simple static ID (e.g., `"local-session"`).
  - Max length: 64 characters (enforced server-side).

- `messages` (array of objects)
  - Ordered conversation history, including user and assistant messages.
  - For each message:

    - `role` (string)
      - One of: `"user"`, `"assistant"`, `"system"`.
      - Validation:
        - Must be one of the allowed roles.
        - The last message in the array **should be a `user` message** for the request to make sense.

    - `content` (string)
      - The textual content of the message.
      - Must be non-empty.
      - Subject to a safe maximum length (e.g., 4000 characters) to avoid abuse.

    - `ts` (string, ISO8601)
      - Timestamp of when the message was created.
      - Example: `"2024-01-26T12:34:56Z"`.

  - The backend enforces:
    - At least 1 message.
    - A reasonable maximum number of messages per request (e.g., 50).

- `client` (object)
  - Information about the client sending the request.

  - Fields:
    - `platform` (string)
      - One of: `"android"`, `"ios"`, `"web"`.
    - `app_version` (string)
      - The version string of the client app (e.g., `"0.1.0"`).

- `settings` (object)
  - Optional tuning parameters for the assistant’s behavior.

  - Fields:
    - `response_style` (string)
      - One of: `"concise"`, `"normal"`, `"detailed"`.
      - Controls how verbose the assistant response should be.
      - Default on the server side is `"normal"` if omitted.

## Response

### JSON Shape

```json
{
  "session_id": "string",
  "reply_text": "string",
  "debug": {
    "model": "mistral",
    "latency_ms": 1234
  },
  "errors": [],
  "actions": [
    {
      "type": "SCHEDULE_LOCAL_NOTIFICATION",
      "title": "string",
      "body": "string",
      "scheduled_for": "ISO8601"
    }
  ],
  "tool_debug": {
    "tool_call": {
      "name": "WEATHER",
      "args": { "city": "Berlin" },
      "confidence": 0.9
    },
    "json_fix_applied": true
  }
}
```

### Fields

- `session_id` (string)
  - Echoed from the request.
  - Allows the client to correlate responses with sessions.

- `reply_text` (string)
  - Natural language reply generated by the LLM or tool execution (or a friendly fallback message if the LLM is unavailable).
  - Intended to be both displayed as text and spoken via TTS.

- `debug` (object)
  - Diagnostic information safe to surface to clients and logs.

  - Fields:
    - `model` (string)
      - Name of the Ollama model used (e.g., `"mistral"`).
      - Derived from backend configuration.

    - `latency_ms` (integer)
      - Total time (in milliseconds) measured on the backend for processing the request, including:
        - Prompt building
        - Ollama/tool routing calls
        - Response assembly

- `errors` (array of strings)
  - A list of **machine-readable** error codes that occurred while handling the request.
  - Example values:
    - `[]` — no known errors.
    - `["ollama_connection_error"]`
    - `["ollama_client_error"]`
    - `["tool_routing_json_error"]`
    - `["tool_execution_error"]`
    - `["unexpected_server_error"]`
  - These codes are simple strings; they may be expanded into structured error objects in later versions.

- `actions` (array of objects, optional)
  - **New in tool-routing V1.**
  - A list of actions for the client to execute locally. Examples:
    - `SCHEDULE_LOCAL_NOTIFICATION`
      - Fields:
        - `title`: notification title.
        - `body`: notification body.
        - `scheduled_for`: ISO8601 timestamp when the notification should fire.
    - `SAVE_NOTE_LOCAL`
      - Fields:
        - `title`: note title.
        - `content`: note content.
        - `created_at`: ISO8601 timestamp when the note was created.
  - Clients that do not support actions can safely ignore this field.

- `tool_debug` (object, optional)
  - Debug information about tool routing, suitable for logs and developer tooling, not for end-user display.
  - Possible fields:
    - `tool_call`: the parsed `ToolCall` JSON the model produced.
    - `json_fix_applied`: `true` if a JSON-fix retry was used.
  - This field may evolve; clients should treat it as opaque debug data.

## Error Handling Philosophy

- `/chat` always attempts to return a **well-formed `ChatResponse`**, even when things go wrong.
- Typical failure cases:

  1. **Validation errors**
     - If the request body cannot be validated against the Pydantic schema (e.g., missing fields, invalid roles), the backend returns a standard FastAPI validation error with HTTP 422.
     - The mobile client should treat this as a programmer/contract issue, not a user-facing “retry later” problem.

  2. **Network / Ollama availability issues**
     - If the backend cannot reach Ollama after a few retries, it:
       - Logs the error with `request_id`.
       - Returns a `ChatResponse` with:
         - A friendly fallback `reply_text` explaining that the assistant is temporarily unavailable.
         - `errors` including `["ollama_connection_error"]`.

  3. **Unexpected server errors**
     - If an unhandled exception occurs inside the `/chat` route:
       - The error is logged with `request_id` and stack trace **in server logs only**.
       - The response to the client is a `ChatResponse` with a generic `reply_text` and `["unexpected_server_error"]` in `errors`.

- **No stack traces or sensitive internals** are ever returned in the JSON body.

## Versioning & Compatibility

- The contract described here is **V1** of the `/chat` API.
- When making backward-incompatible changes:
  - Update:
    - `context/API_CONTRACT.md`
    - `context/DECISIONS.md`
    - `context/CHANGELOG.md`
  - Consider one of:
    - A new versioned path (e.g., `/v2/chat`).
    - Backward-compatible fields with sensible defaults.

This document should always be treated as the **source of truth** for `/chat` behavior and shape.
